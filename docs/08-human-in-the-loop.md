# 08 — Human-in-the-loop (HITL)

---

## Pattern นี้คืออะไร?

Human-in-the-loop คือการให้ **มนุษย์เข้ามามีส่วนร่วม** ในกระบวนการทำงานของ Agent ในจุดที่ต้องการการตัดสินใจ การอนุมัติ หรือการตรวจสอบก่อนดำเนินการ

```
Agent ต้องการทำ Action ที่ต้องการ Approval
  │
  ▼
[Request Approval] ──→ ส่งคำขอให้มนุษย์ตรวจสอบ
  │
  ▼
มนุษย์:
  ├─ Approve ──→ Agent ดำเนินการต่อ
  ├─ Reject ───→ Agent ยกเลิก
  └─ Modify ───→ มนุษย์แก้ไข → Agent ดำเนินการ
```

---

## เมื่อไหร่ควรใช้

- การกระทำที่มีผลกระทบสูง (ส่งอีเมล, สั่งซื้อ, ลบข้อมูล)
- การตัดสินใจที่ต้องใช้ดุลยพินิจของมนุษย์
- งานที่ผิดพลาดแล้วแก้ไขยาก
- ระบบที่ต้องการตรวจสอบก่อน deploy

**ตัวอย่าง:**
- อนุมัติการสั่งซื้อ
- ตรวจสอบเนื้อหาก่อนส่ง
- ยืนยันการเปลี่ยนแปลงข้อมูลสำคัญ
- Escalation เมื่อ Agent ไม่แน่ใจ

## เมื่อไหร่ไม่ควรใช้

- งานที่ต้องการ automate 100%
- งานที่ปริมาณมากเกินกว่ามนุษย์จะตรวจสอบ
- งานที่มนุษย์ทำช้า ทำให้ระบบกลายเป็น bottleneck
- งานที่มนุษย์มัก approve โดยไม่อ่าน (rubber-stamping)

---

## ข้อดี

- **ปลอดภัย** — มนุษย์ตรวจสอบก่อน action สำคัญ
- **ลดความเสี่ยง** — ป้องกัน Agent ทำผิดร้ายแรง
- **เพิ่มความเชื่อมั่น** — ผู้ใช้รู้สึกควบคุมได้
- **เก็บข้อมูล** — ประวัติการอนุมัติใช้ปรับปรุงระบบได้

## ข้อเสีย

- **ช้า** — การรอมนุษย์เป็น bottleneck
- **Scale ไม่ดี** — ถ้าต้องตรวจสอบทุกอย่าง จะต้องใช้คนมาก
- **Human Error** — มนุษย์ก็ approve ผิดพลาดได้
- **UX ซับซ้อน** — ต้องออกแบบระบบ approval ที่ดี

---

## Checkpoint ประเภทต่างๆ

| ประเภท | วิธีการ | เหมาะกับ |
|---|---|---|
| Pre-approval | ขออนุมัติก่อนดำเนินการ | Action สำคัญ |
| Post-review | ดำเนินการก่อน แล้วให้ตรวจสอบทีหลัง | Action ความเสี่ยงต่ำ |
| Escalation | เฉพาะกรณี Agent ไม่แน่ใจ | คำถามก้ำกึ่ง |
| Scheduled | ตรวจสอบเป็นรอบ | งานที่ทำเป็น batch |
| Exception-only | เฉพาะเมื่อผิดปกติ | ระบบที่ stability สูง |

## การทำงาน

### ตัวอย่าง: Email Assistant

```
User: "ส่งอีเมลแจ้งลูกค้าทุกคนโปรโมชั่นใหม่"

Step 1 — Agent Draft Email
  สร้างร่างอีเมล: "เรียนลูกค้าที่เคารพ..."
  ระบุจำนวนผู้รับ: 1,250 คน

Step 2 — Request Approval
  ส่งให้มนุษย์ตรวจสอบ:
  - เนื้อหาอีเมล
  - รายชื่อผู้รับ
  - เวลาที่จะส่ง

Step 3 — Human Decision
  ├─ Approve → Agent ส่งอีเมล
  └─ Reject → Agent ยกเลิก
      (หรือรอให้มนุษย์แก้ไขแล้ว Approve ใหม่)

Step 4 — Confirmation
  แจ้งผล: "ส่งอีเมลเรียบร้อย 1,250 คน"
```

---

## ข้อผิดพลาดที่พบบ่อย

1. **ขออนุมัติทุกอย่าง** — ทำให้มนุษย์ล้าและไม่สนใจของสำคัญจริงๆ
2. **Human Bottleneck** — ระบบทำงานไม่ได้ถ้ามนุษย์ไม่ตอบ
3. **Rubber-stamping** — มนุษย์ Approve โดยไม่อ่าน
4. **ไม่ให้ Context พอ** — มนุษย์ไม่รู้จะตัดสินใจอย่างไร
5. **Timeout ไม่เหมาะสม** — ถ้ามนุษย์ไม่ตอบ ควรทำอย่างไร?

---

## Design Guidelines

1. **ขออนุมัติเท่าที่จำเป็น** — เลือกเฉพาะจุดที่มีความเสี่ยงสูง
2. **ให้ Context ที่เพียงพอ** — มนุษย์ต้องตัดสินใจได้โดยไม่ต้องหาข้อมูลเพิ่ม
3. **มี Timeout Policy** — เมื่อมนุษย์ไม่ตอบภายในเวลาที่กำหนด
4. **Mobile-ready** — approval ต้องทำได้ทุกที่
5. **Audit Trail** — บันทึกทุกการตัดสินใจ
6. **Feedback Loop** — ใช้ข้อมูลการอนุมัติเพื่อปรับปรุงระบบ

---

## Safety และ Verification

- ตรวจสอบว่ามนุษย์ที่ approve มีสิทธิ์เพียงพอ
- Log ทุก action และ decision
- มี mechanism ย้อนกลับเมื่อ approve ผิด
- แจ้งเตือนเมื่อ approval ค้างนานเกินไป
- ทดสอบ Human-in-the-loop flow เป็นประจำ

---

## สรุป

Human-in-the-loop สร้างสมดุลระหว่าง Automation และการควบคุมโดยมนุษย์ ทำให้ระบบปลอดภัยขึ้นโดยที่ยังคงประสิทธิภาพไว้

**ข้อควรจำ:** ยิ่ง HITL checkpoint เยอะ = ยิ่งปลอดภัย แต่ก็ยิ่งช้า หาจุดสมดุลให้เจอ
